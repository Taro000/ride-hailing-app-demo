# Conventions shared by the design skills

Six skills turn a system's requirements into its design. Five are stages that run in order: 1, 2, 2b, 3 and 4. The sixth reviews the output of stages 2, 2b, 3 and 4. A seventh, `design-chain`, runs the others for the user in Claude Code: the stale stages and the reviews that are due, each as a subagent ("Stale stages"). It writes no design item itself.

| Stage | Skill | Reads | Writes |
|---|---|---|---|
| 1 | `requirements-to-architecture-drivers` | the quality chain's artifacts, the design context the user gives (technology, budget, deadline, team, anticipated changes), existing code | `design-context.yaml`, architecture drivers (DRV), assumptions (DAS), hand-offs (HND) |
| 2 | `architecture-drivers-to-architecture` | DRV, the design context, functional requirements and CUJs, the hand-offs addressed to it | design decisions (DEC), elements (ELM), views, DAS, HND |
| 2b | `architecture-to-technical-policy` | ELM, DEC, DRV, the design context (technology constraints, the organization's engineering standards among them; the team; the conventions of the existing code), the quality chain's gates and audits and its maintainability requirements, the hand-offs addressed to it | technical policies (POL), DEC, DAS, HND |
| 3 | `architecture-to-high-level-design` | ELM, DEC, POL (how each kind of interface gets its spec, and the conventions inside the code), DRV, acceptance criteria, SLI definitions, the hand-offs addressed to it | interfaces (IFC) and their specs, data entities (DAT), DEC, DAS, HND |
| 4 | `high-level-design-to-detailed-design` | one component per run, with its IFC, DAT, DEC, DRV, functions, the POL that bind every component (its stack, directories and dependency rules, test layers and the conventions inside the code) and the hand-offs addressed to it | modules (MOD), DEC, DAS, HND, the detailed design index |
| Review | `design-review` | the output of stage 2, 2b, 3 or 4, and what it was built from | a review report, findings (FND), DAS |

Each stage turns the decisions of the stage above into obligations for the stage below: an architecture decision binds the technical policy and the high-level design, a technical policy binds the high-level design, the detailed design and the code of every component, and an interface binds the modules that realize it. Every item traces up to what it serves, so anyone can walk from a module back to the driver, the quality requirement and the user behind it. What a stage leaves undecided, it hands off to the stage that will decide it ("Decision depth", "Hand-offs"). What the quality chain should change, any stage or review writes as a request to the quality chain ("Requests to the quality chain").

## The quality chain

The quality chain is the set of four skills that write `docs/quality/`. It produces what the design starts from: users, CUJs and shared facts (`context.yaml`), quality-in-use requirements (QIU), functional requirements (FR) with acceptance criteria, product and data quality requirements (QR) with their handling, non-functional requirements (NFR), SLI definitions (SLI), error budget policies (EBP) and its own assumptions (QAS).

The quality chain states requirements and never decides design. What it leaves to the design:

- The design decisions it found in its inputs, under `design_inputs` (DIN) in `context.yaml`. Stage 1 takes each one in as a technology constraint candidate.
- Platforms and device support. The quality chain names only kinds of device and situations in its contexts of use. Operating systems, browsers, versions, and native or web are a technology constraint when the input fixes them, and otherwise a stage 2 decision.
- Mechanisms. Its functional requirements state behaviour observable from outside; the keys, tokens, IDs, caches, retries and queues that produce that behaviour are design decisions.
- Where SLI events come from. Its SLIs are defined in the terms of the domain: the unit event, the vantage (`user-side`, `system-boundary`, `synthetic` or `data`), the counting rules. Stage 3 binds every SLI to the interface or data that produces its events, with the fields and the method (`sli_bindings`), without changing what the SLI counts.
- Where gates are checked and audits held. Its gates (NFRs of kind `gate`) say where they run (CI, a release check or the Definition of Done), what they check and the threshold; its audits (kind `audit`) say the mechanism, the criterion and the cadence or deadline. Stage 2b binds every gate to the step and the check that realize it (`gate_bindings`), and places every audit (`audit_bindings`), without changing what either requires.

The design, in turn, never decides or changes what the quality chain owns: its users and CUJs, the functions and their acceptance criteria, the quality requirements and their handling, the NFRs (SLOs, gates, audits and monitors) with their targets and thresholds, the SLIs and what they count, the error budget policies and the shared facts. A level that the system's quality must reach, and a check that the work must pass on a quality requirement before it is merged, shown, released or called done, are requirements even when the design is the first to see the need for them: the second is a gate, which the quality chain places in CI, at a release check or in the definition of done. Write a request for either ("Requests to the quality chain"), and never make it a decision, a parameter, a verification or a criterion of the design. How the design meets the requirements is design: a latency budget that splits an SLO's threshold, a parameter that tunes a mechanism (the error threshold of a breaker, a timeout), and how a part is verified, a check in CI that the code keeps a decision of the design included (module dependencies in their direction, the shared fields in every log line).

Rules for using it:

- Read it; never write to it. Do not edit, add or retire anything under `docs/quality/`, do not write function proposals there, and do not record answers in its QAS files.
- When the design shows that something in the quality chain should change, or that something the design needs from it is missing, write a request to the quality chain ("Requests to the quality chain"). The user answers it and hands the request document to the quality chain; afterwards, the design stages that the change reaches are re-run.
- Refer to chain items by their IDs, including its shared facts (CON, EXT, OPF). Do not copy their statements into design items; trace to them.
- A chain item's `basis_note` may say what the design must confirm. Stage 1 turns each such point into a driver, a constraint, a question, an assumption (DAS), or a hand-off (HND) to the stage that designs the part. That stage decides the hand-off by confirming the point, citing it in `basis_note`, or writes a request to the quality chain when the design shows that the point does not hold.
- When `docs/quality/` does not exist, accept the same information from the user (users, CUJs and their steps, functional requirements with acceptance criteria, quality requirements with their priority, targets that can be measured) and record where it came from in the report's "Inputs" table. In trace fields, write the source instead of an ID ("PRD, section 3"). Requests then go to the user, who keeps those requirements: their `targets` name the sources, and `quality_stages` is empty.

### Requests to the quality chain

A request (QCR) asks the quality chain for one change. Each one is a file in `qcr/` (`artifacts.md`). `scripts/tables.py` writes every request that is open or answered into one document, `docs/design/quality-chain-requests.md`, which the user hands to the quality chain. Write a request when the design shows:

- a target that no design within the budget, the deadline and the team can meet, or a conflict between requirements that no design resolves;
- a function the design needs that no FR provides (a reconciliation, a way out of a state), or a CUJ step that no FR covers;
- a requirement that contradicts another chain item or the design context, or that is ambiguous where a design decision depends on it;
- a technology constraint that the user keeps, and that limits what users can do;
- a shared fact that is missing or no longer holds, or a chain item that states a design decision;
- an SLI that no binding can realize as defined;
- a gate, a target or a threshold that the design finds the system needs;
- the user's answer to a question about a QAS ("Assumptions").

A request names the chain items it asks to change, or that show what is missing (`targets`); the design items that show the issue (`origin`); the issue; the change it suggests; and the quality-chain stages that would make the change (`quality_stages`): stage 1 for the context (users, CUJs, shared facts, design inputs) and the quality-in-use requirements, stage 2 for the functions, stage 3 for the quality requirements and their handling, stage 4 for the NFRs, SLIs and error budget policies, and for a QAS the stage that wrote it. Name only the stages that make the change; the later quality-chain stages follow it on their own re-run. Write one request per change. When an open request already asks for the change, write no second one: list it in the `premises` of this stage's items that depend on it, and when this stage needs the change to say more, write a request for only what it adds, naming the open one in its `issue`.

Rate its impact by what the design would have to redo if the quality chain decided otherwise:

- `high` when the answer could change an existing item of the full-depth kinds of the stage that writes it ("Decision depth"), or a primary driver: what its scenario asks, or whether it stays above the primary line. Ask it in this run, as a point that rates high ("Draft first, ask afterwards"), and proceed on the answer: record the question and its answer under "Decisions" and in the request, and the items that depend on it cite the answer in `basis_note`. When nobody can answer during the run, the question waits under "Unanswered questions" like any other and names the request; the user may answer it there or under the request in the request document, and the run that applies the answer takes it from either.
- `low` otherwise, such as a request that adds a check before release or makes a counting rule precise without changing what any of those items must do. Do not ask; proceed on the requirements as `docs/quality/` states them now.

A request about a contradiction between chain items is asked whatever its impact, as every contradiction is ("Draft first, ask afterwards"): the design cannot tell which side to follow. When the other side is the design context or a decision the user confirmed, the design follows that side, and the request is rated like any other.

Every item that would change with the request lists it in `premises`, whichever stage or review raised it, so that the items to revisit are found when it is answered or applied; an item that rests on a QAS whose answer the request carries lists the QAS instead. A request in `premises` does not make an item `assumed`: the item follows the current requirements, or the user's answer.

A request is `open` until the user answers it: in a question, in the request document, or by telling a later stage. It is then `answered`, or `withdrawn` when the user decides that the quality chain need not act on it; the stage that raised it also withdraws it when the design no longer needs it. A request that carries the answer to a QAS stays `answered` whatever the answer, since the QAS still has to record it. A request is `applied` once `docs/quality/` shows the change, or the quality chain's report records its decision on it. Applied and withdrawn requests leave the request document; items may keep them in `premises`.

On every run:

- The user may write an answer in the request document, after "Answer:" under a request. Such an edit is a hand edit ("Re-running a stage"): record it in the request as the user wrote it (the answer, `answered_in: quality-chain-requests.md`, and the status) before running `scripts/tables.py`, which rewrites the document from the requests. Apply any other edit to the document to the requests it concerns in the same way. The script stops with a message rather than drop an answer, or other text written by hand, that the requests do not hold.
- Read what changed under `docs/quality/` since this stage last ran, and set each request that those changes apply to `applied`.
- List in the `premises` of this stage's items the open and answered requests that would change them, whichever stage or review raised them. Re-rate the open ones, and ask those whose impact is now high. Items of this stage that depend on an answered request follow the answer and cite it in `basis_note`; once the request is applied, they follow `docs/quality/`, as for any upstream change.

The stage or review that raises a request owns its content. Any stage or review records its `status`, `answer` and `answered_in`, and re-rates its `impact` and `impact_note`; when an answer asks for another change than the one suggested, the run that records it also fits `targets` and `quality_stages` to the answer.

## Decision depth

Details settled early are redone whenever a later stage, or the code, learns what the early stage could not know. Each stage therefore decides in full only what is hard to change once other work builds on it, and leaves the rest to the stage that will know enough to decide it.

A stage decides each point that its workflow meets at one of three depths:

| Depth | The stage | Example |
|---|---|---|
| Full | Decides it in every detail, in its items | The owner of a data entity; the contract of an interface with an external system; a vendor |
| Bounds | Decides only the promise that later stages keep, and defers the detail | "Every operation that moves money is idempotent, with one key per order", and no table of the key of each operation |
| Hand-off | Decides none of it, and hands it off: to whom, when, and within which bounds ("Hand-offs") | The timeout values inside a component, to stage 4; the details of a library, to implementation |

Implementation, the coding that follows stage 4, decides whatever no stage does; the code and its tests hold what it decides, and nobody writes it back into the design. When the code cannot keep a decision the design made, implementation raises a finding ("Findings between design stages").

### Full-depth kinds

Each stage decides the kinds of point in its row in full, whatever their ratings. The last column names what it typically leaves to others, and to whom.

| Stage | Decides in full | Leaves to others |
|---|---|---|
| 1 | The ranking of the drivers and where the primary line falls; the non-negotiable constraints | How hard each driver below the primary line is, beyond what places it there (stage 2 checks whether its decisions meet it); the points that quality-chain items leave for the design to confirm, to the stage that designs the part |
| 2 | The overall structure; the platforms and device support; the runtime of each component; the deployment: where each element runs; where each kind of data lives and which element owns it; the shape of each integration with an external system, behind an adapter of its own; the sizes that are paid for or hard to change once built, such as the capacity in a contract or the number of partitions of stored data; the trust boundaries; the principles of the mechanisms that span elements: which parts hold state, no transaction across a call to another element, which operations are idempotent and what their keys cover, how an unknown outcome is held and settled (from when its wait counts, and what is undone when it is treated as not having happened), where events are delivered from and that none is lost, and the order of the timeouts along each call path | The tables of single operations (their keys, error codes and retries), to stage 3; the values of timeouts, waits, intervals and thresholds, within that order: to stage 3 on the paths of time SLOs and of money, otherwise to stage 4; within the runtime and the platform it decides, the language, framework and libraries of each kind of component, the repositories and the layout of the code, the tests and the pipeline, and the conventions inside the code, to stage 2b |
| 2b | For each kind of component (a server, a web app, a batch job): its language, framework and main libraries, within the runtime and the platform that stage 2 decides, with the package manager, the build and the tool that changes database schemas. The repositories and the components each holds, the layout of their directories, and the dependency rules, each with the check in CI that enforces it. The test layers, the test doubles of external systems, the clock and IDs, and the environments with their test data. Where and by what each gate of the quality chain is checked, and where each of its audits is held. The pipeline, what blocks a merge or a release, and how a release is deployed and rolled back; the static checks; how the code handles errors, writes logs, reads settings and secrets, and keeps the texts for people. For each kind of interface, whether its spec is written by hand or generated from the code. How coding agents find the design, and how implementation's findings come back | The libraries that only one component needs beyond the main ones: to implementation, within the stack, or to stage 4 for that component, by a hand-off, when a module that stage 4 designs in full depends on the choice. The versions of every library and tool, the configuration of each tool, the files of the pipeline, the tests and the test data: to implementation, within the policies. The conventions that interfaces show to their consumers (errors, IDs, time, money, paging, tokens, versioning, the headers of idempotency keys and request IDs, the log fields that SLIs need, naming) are stage 3's |
| 3 | Every interface whose spec the technical policy says is written by hand, because its other side is built apart from this system's code: its whole contract, schema included. Every other interface between elements, an external system's included as far as the design relies on it: its operations, its errors and their codes, what its idempotency keys mean, and the states and events its consumers see. The shared conventions that interfaces show to their consumers, the codes for errors in fields included; how a call whose outcome is unknown sorts its results and answers its caller (the pending answer and its code); the states across elements of every entity that holds money, a booking or an unknown outcome; the consistency rules, retention and classification of every data entity; the latency budget of every SLO with a time threshold, and the timeouts and waits on its path and on every path that moves money, with the other values that stage 2 leaves on those paths (thresholds, intervals, cache lifetimes); where every SLI's events come from | The schema of every interface whose spec the technical policy says is generated from the code, to implementation, which generates it; the timeouts and other values of other calls, within the order stage 2 decides, to stage 4; the attributes of data entities beyond what shows what each one is, and the lists and mechanisms kept inside one element (the types of its records, how it tracks what it has delivered), within the promise its consumers see: to stage 4 where it decides them in full, otherwise to implementation. The conventions inside the code (how errors are passed on, how logs are written, how settings and secrets are read, where the texts for people live) are stage 2b's |
| 4 | Every module that moves money, settles an unknown outcome, shares state with work that runs at the same time, applies rules with several conditions, or migrates data, at full depth: its states, its decision tables (the one that settles each unknown outcome included), its concurrency, the values of its parameters, what keeps the invariants of its data, and its migrations. Every table that another component reads directly, in full | The inside of every other module, its parameters included, to implementation, within its responsibility, the summary of its contract, the acceptance criteria allocated to it and its checks; the rest of the physical data (tables, columns, types, indexes for queries), to implementation, within the data entities: their attributes and relations, owner, consistency rule, classification and retention. The stack, the directories and dependency rules, and the test layers are stage 2b's, for every component: a library is stage 4's only when stage 2b hands its choice to it for the component |

### Deferring the rest

A point outside the stage's full-depth kinds is still decided in full when it rates high on breadth or severity ("Draft first, ask afterwards", step 5). Rate it as it would stand once deferred, within the bounds this stage decides: most details rate low once the bounds hold what is hard to undo, such as the key of one operation once the scope of keys is decided, or the type of a column once the entity's invariants are.

Every other point is deferred; that is the default.

- Decide its bounds when later stages, or several elements, must keep one promise about it, and defer the detail. State the bounds in the terms of what crosses the boundary: a promise that copies a list kept inside one element (the types of its records, the attributes it stores) changes whenever that list does.
- Leave what is deferred to the stage that will decide it, with a hand-off where "Hand-offs" asks for one. Deferring a point outside the stage's full-depth kinds is how the chain divides its work: it is not a business decision, it is not asked, and it needs no assumption. The stage that decides the point rates it then.
- Deferring a point of the stage's full-depth kinds, or one that rates high, is a business decision ("Decisions"), such as waiting for a contract before choosing a vendor. Ask about it when either rating is high; otherwise adopt it provisionally as a DAS of kind `decision`. Its hand-off goes to the stage that decides the point once its trigger comes.

A point that no step of the stage's workflow designs is not deferred by it: it is the work of the stage that designs it, as the schema of an interface is stage 3's while stage 2 decides the structure.

## Hand-offs

A hand-off (HND) carries one deferred point to the stage that will decide it, or to implementation. Each one is a file in `hnd/` (`artifacts.md`), so that a stage, or a script, finds the open hand-offs addressed to it by their `to` and `status`.

Write a hand-off for a point this stage defers when the stage it goes to would not take the point up otherwise, or when one of this stage's exit criteria asks for the point ("Exit criteria"). A criterion asks for one when it says that the point is handed off with its stage and trigger; a criterion that asks only for the later stage that decides a point, and when, is met by naming them in the report, as long as that stage's full-depth kinds or workflow cover the point. A point that a later stage's workflow designs anyway needs none: stage 3 gives every interface its idempotency, within what stage 2 decided the keys cover, without a hand-off. Stage 1 writes one for each point that quality-chain items leave for the design to confirm and that it does not settle itself ("The quality chain").

- `what`: the point, not an answer to it.
- `to`: the stage that will decide it: the first later stage whose full-depth kinds include it, otherwise the stage that designs the part it belongs to, otherwise `implementation`. When only an event outside the chain can settle it (a measurement in operation, a signed contract, a date), address it to the stage that decides it once the event comes, which may be this stage.
- `component`: for a hand-off to stage 4 or to implementation, the component it concerns; write one hand-off per component. A stage that cannot name the component yet (stage 1) addresses the point to the next stage, which passes it on.
- `trigger`: when it falls due: that stage's next run, its run for the component, the implementation of a named part, or the event. An event has come when the inputs show it or the user says so.
- `bounds`: what the decision must keep, by the IDs of the items that set it, each with a short label and never a copy of its content. `origin`: the items the point comes from.

Every stage reads the open hand-offs addressed to it on every run (stage 4: those for its component), and takes up each one whose trigger has come:

- Decide it: decide the point in this stage's items, within its bounds, and cite the hand-off in their `basis_note`; set `status: decided` and name the items in `resolution`. A point that a quality-chain item leaves for the design to confirm is decided by confirming it, or by writing a request to the quality chain when the design shows that it does not hold.
- Or pass it on, when the point is not of this stage's full-depth kinds and does not rate high here: set `to`, `component` and `trigger` as for a new hand-off, and write why in `resolution`. Bounds this stage adds go in its own items, which `resolution` names.
- When the point cannot be decided within its bounds, write a finding addressed to the stage that set them ("Findings between design stages").

The stage that writes a hand-off owns `what`, `bounds` and `origin`. The stage it is addressed to records only `status`, `to`, `component`, `trigger` and `resolution`, as it would on a finding. When nothing needs a hand-off any more (its origin was retired, or a later decision made it moot), either of them sets `status: retired` and says why in `resolution`.

A hand-off addressed to implementation stays open in the design: whoever implements the part reads it, and the code and its tests decide it. Stage 4 lists the open ones in the hand-off to implementation of its index (`artifacts.md`).

## Exit criteria

A stage's exit criteria check that what is hard to change was decided at the right stage, not that every detail was written down.

- A criterion that asks for a detail takes the form "every X has Y, or Y is handed off with its stage and trigger". A Y handed off that way is not missing: no later stage and no review counts it as a gap.
- Every stage also meets these, whether or not its skill lists them: no point of its full-depth kinds, and none that rates high, is handed off unless its deferral was decided as a business decision ("Deferring the rest"); every open hand-off addressed to it whose trigger has come is decided or passed on ("Hand-offs"); no item decides or changes what the quality chain owns; and every request to the quality chain of high impact that this run raised, or that its items depend on, was asked ("The quality chain").

## Findings between design stages

A later stage, a review or implementation that finds a problem in an earlier design stage's items writes a finding (FND) addressed to that stage. It never edits that stage's items itself, so that every item has exactly one stage that writes its content. (Assumption files, hand-offs and findings also record answers and statuses from other stages, as described in "Assumptions", "Hand-offs" and below.)

- A finding names the skill it is addressed to, the items it concerns, its severity, the evidence and a suggested resolution.
- Implementation raises a finding, with `raised_by: implementation`, only when the code cannot keep a decision the design made: a contract, an invariant, an interface, a policy or a decision that does not work as written, or two items that contradict each other. What the design leaves to implementation is decided in the code and its tests; it is never a finding and never written back into the design. Stage 4 writes this rule at the top of the hand-off to implementation in its index (`artifacts.md`), where coding agents read it.
- Every stage reads the open findings addressed to it, on every run. For each one, it accepts (changes its items and cites the finding in their `basis_note`) or rejects (writes why in `resolution`), and sets the finding's status. A rejection that leaves a risk in place is a business decision ("Decisions").
- Only a critical or major finding is a reason to run the stage it is addressed to. A minor finding waits until the stage runs for another reason, such as a change upstream, a hand-off whose trigger has come, or a critical or major finding, and that run processes it with the others. Never name a stage to run when its only reason would be its open minor findings.
- `design-review` reviews each of stages 2, 2b, 3 and 4 after its first run (stage 4 after the first run for each component). The review of a stage is repeated only when a critical or major finding changed the stage's items: the stage accepted one addressed to it, or it followed the change that an earlier stage made to accept one that the stage's own review raised. The repeated review covers only what changed since the last one. Items changed only for minor findings, or only to follow other changes upstream, call for no review: the next review of the stage covers them too.
- When an accepted finding changes items, tell the user which later stages to re-run and whether to repeat the review, as "Finishing a run" describes.
- A finding is about this design. A problem in the quality chain is a request to the quality chain ("Requests to the quality chain"), not a finding.
- What `scripts/check.py` checks is not raised as a finding ("Scripts"). The one exception is a problem in a stage's own items that only an earlier stage can fix, such as an interface that carries a function its provider does not have: the stage writes a finding addressed to the earlier stage that targets the earlier stage's item and names the value (the FR, the driver), and the check shows the problem as waiting for that finding.

## Scope

These skills design software for the system inside the boundary in `context.yaml`, or inside the boundary the user gives: its structure, interfaces, data, modules and deployment. The infrastructure the software runs on (runtime environments, networks, managed services) is in scope as part of the deployment design.

Business procedures, operating runbooks and training are not. When only they can meet a need, write one line in the report's "Out of scope" section saying what and why. Systems outside the boundary appear only as external systems. What an external system promises (an SLA, a rate limit) is a technology constraint (TC) that decisions and interfaces cite by ID; what the design assumes beyond that is a DAS.

## Working language

- Ask questions in the language the user writes in.
- Write artifacts in the language of the project's existing documentation. If the project has none, use the user's language.
- Keep YAML keys, IDs and enum values in English exactly as `artifacts.md` defines them, so that every stage can read every other stage's files. Write free-text values in the working language.
- Use the terms in `glossary.md` for the working language, and use each one consistently.
- When you name a quality characteristic, use the name the quality chain's own report uses for the working language.
- Write diagram labels in the working language and keep IDs in them as they are.
- In reports, write the basis marks and statuses with the glossary's terms for the working language. In YAML, use the English enum values.

## Judgment basis

Mark every judgment with where it came from:

- `stated`: written in the input, in the quality chain's artifacts or in an earlier design stage's items. Rewording that keeps the meaning is still `stated`.
- `inferred`: your own judgment, made with enough evidence that you are not unsure. Anything the input does not say is `inferred` or `assumed`, even when it seems obvious. A design decision you make is `inferred` until the user confirms it.
- `assumed`: your own judgment that you were unsure about and did not ask about, because it fell below the bar for questions ("Draft first, ask afterwards"). It is recorded as an assumption (DAS), and every item that depends on it lists the DAS in `premises`.
- `confirmed`: the user answered a question about it.

Never present an `inferred` or `assumed` judgment as if it were `stated`. People tend to accept a confident-looking draft without checking it; the basis mark tells them where to look.

An item holds several judgments, and its `basis` is the weakest of them, from weakest to strongest: `assumed`, `inferred`, then `stated` and `confirmed`. An item is `confirmed` only when every judgment in it that is not stated has been answered. When the parts differ, say in `basis_note` which parts are stated, inferred, assumed and confirmed. Most design items stay `inferred`: they are proposals built on the stages above.

Stage 1 writes `design-context.yaml`. A later stage or a review that learns a new fact from the user (an SLA, a volume, a change in the team) adds the entry itself and says so in its report.

An item lists in `premises` what it relies on directly that could change under it (it does not copy the premises of the items it traces to, which are found by following the traces): the design context's entries (TC, PC, TEAM, CHG, STK), assumptions (DAS), the quality chain's shared facts and assumptions (CON, EXT, OPF, QAS), and the requests to the quality chain (QCR) that would change it. Refer to such an entry by its ID, and copy neither its values nor its wording beyond a short label.

## Numbers

- Business numbers (targets, deadlines, thresholds, volumes, budgets) come from the inputs: the quality chain's items, the design context or the user. Never invent one. Use the chain's values and the names of its placeholders as they are. A number the design needs that no input gives is a gap: ask for the fact that would settle it, or write a named placeholder whose name no other placeholder uses, and list it in the report under "Placeholders". When the missing number is a target or a threshold that the system's quality must reach, it is a requirement: write a request to the quality chain as well ("The quality chain").
- Design parameters (timeouts, retry counts and back-off, pool and batch sizes, cache lifetimes, partition counts) are design decisions. Propose a provisional value and say what it is based on (a stated number it derives from, a calculation, the default of a named library or service). A provisional parameter is a decision ("Decisions"). A stage sets a parameter's value only when the parameter is of its full-depth kinds or rates high; otherwise it leaves the value to a later stage, within the bounds the value must keep ("Decision depth").
- Show in the report how every derived number (a latency budget, a capacity estimate, a storage estimate) follows from stated numbers. Compute with a script, not by hand.

## Existing systems

When the repository holds code or infrastructure definitions for the system:

1. Stage 1 reads them before drafting and records the current structure in `design-context.yaml`: elements, data stores, deployment, dependencies, and the conventions the code follows.
2. Later stages read the parts they design, and design changes as deltas: every element, policy, interface, data entity and module is marked `keep`, `change`, `new` or `remove`.
3. Say in the report what was read, and what the code cannot tell (runtime behaviour, production configuration, real volumes). Never present a guess about runtime behaviour as something read.

When there is no code, every item is `new`.

## Draft first, ask afterwards

1. Read every input: the quality chain's artifacts (or what the user gave instead), `design-context.yaml`, this stage's existing items and the items of the stages above it, the open findings and hand-offs addressed to this stage, the requests to the quality chain that are open or answered (`qcr/`, and the answers the user wrote in `quality-chain-requests.md`), and the code the stage needs. On a re-run, start from what changed ("Re-running a stage").
2. If an essential input is missing, so that no meaningful draft is possible (each skill names its essential inputs), ask only for that input before drafting. This is a request for input, not a judgment question. When nobody can answer during the run (step 7), write the request for input down as step 7 does, in a report that holds only its header when the stage has none yet, and finish the run without drafting.
3. Draft the whole stage without stopping. Make every judgment yourself, using the rules in the skill. Decide each point at the depth "Decision depth" gives it, and write the hand-offs for what you defer. Write the items as you draft them, and the draft report that indexes them. Work in parts small enough to write as you go (one group of related items at a time, such as the interfaces of one element), and write each part's items before you start the next: a stage worked out in full before the first file is written saves nothing if the run stops.
4. List every point you were unsure of. A point is uncertain when:
   - the input is silent or ambiguous about a fact the choice depends on, and the choice changes this stage or a later one;
   - two or more reasonable options exist, and the wrong one would cause rework downstream;
   - inputs contradict each other, the quality chain or an earlier design stage;
   - it depends on facts that only the user's organization knows: budgets, contracts, team skills, existing systems, operating practice, volumes;
   - it is a business decision ("Decisions").

   A design choice you make with the skill's rules from what the inputs state is not uncertain only because the inputs did not make it for you: making it is this stage's job, and it stays `inferred`. A point you defer because the stage's full-depth kinds do not include it is not an uncertain point of this stage; the stage that decides it rates it then. Never list anything the input already states, wording, or how the method works; do list the facts that a judgment made with the method depends on. Merge points that hinge on the same fact.
5. Rate each point on two scales:
   - Breadth, read from the structure rather than guessed:
     - high: it changes the structure (an element, a boundary between elements, the owner of a data entity, the deployment), a technology constraint, the ranking of the primary drivers, a shared convention, the language, framework or repositories of a kind of component, or an interface that more than one element uses; or five or more items depend on it, counting the items of later stages through their traces once those exist;
     - medium: two to four items depend on it;
     - low: one item depends on it.
   - Severity, the harm if the draft is wrong and nobody notices until later:
     - high: legal, safety, financial or personal-data harm; something hard to reverse later (the shape of stored data, a published interface, a contract, a vendor or a framework the system becomes tied to); or a primary driver, a non-negotiable constraint or a CUJ that the design no longer meets;
     - medium: several items would have to be redone, but no harm reaches users or the business;
     - low: easy to change later, such as a choice inside one module or a provisional parameter that is tuned in operation anyway.
6. Ask about a point when either rating is high. Ask also, whatever the ratings, about a contradiction between inputs, with the quality chain or with an earlier design stage (a requirement that contradicts the design context or a decision the user confirmed is a request to the quality chain instead, rated like any other), about the content of a law, standard, contract or policy that the inputs name but do not give, when a judgment in this stage depends on it, and about each request to the quality chain whose impact is high ("Requests to the quality chain"). There is no fixed number of questions; the ratings decide. Every other point becomes an assumption ("Assumptions"): keep the drafted judgment, mark it `assumed`, and write a DAS item.
7. Ask in order of breadth × severity, high and high first, grouped by theme. For each question, give what you drafted, why you are unsure, and the options, with your drafted answer first. When a question asks for a fact (a budget, a name), the drafted option says what the draft does without it ("left as a placeholder"), and the user types the value.
   - When several items share one yes-or-no judgment ("which of these components does the team already run?"), ask it as one multi-select question rather than one question per item.
   - If a structured question tool is available (for example, AskUserQuestion in Claude Code), ask up to 4 questions per call with 2 to 4 options each, put your drafted option first and label it as recommended, and call the tool again for the next batch. Ask multi-select questions with up to 4 items each, splitting longer lists over several questions.
   - Otherwise, ask in chat as a numbered list and wait for the answers.
   - When nobody can answer during the run, write the questions down instead of asking them. That is the case when the stage runs as a subagent of another agent (a Claude Code subagent cannot ask the user), when nobody watches the run, or when the request says to write the questions down. It holds for every question that these conventions or the skill ask during a run. A person who runs the stage directly is asked during the run, as above.
     - Write each question as a row under "Unanswered questions" in the report, in the order you would ask them: its number, which it keeps under "Decisions" ("Re-running a stage" says how rows are numbered); the question; why you are unsure; the options as a question tool would show them (2 to 4, the drafted one first and marked as drafted; for a multi-select question, up to 4 items, with the drafted choice); the items the answer bears on; and an empty answer. In the `basis_note` of each of those items, say that the judgment waits for the question ("the browsers wait for question 4").
     - Write no finding that rests on one of these questions until it is answered: once written, a finding is settled only by the stage it is addressed to.
     - Set the report's status to "waiting for answers", skip step 9, and finish the run (step 10): the items are committed as drafted, with the assumptions of step 6.
     - The answers come from the user. The user writes each one in its question's row, or the agent that started this run writes there what the user answered. An agent never answers in the user's place, since an answer makes the judgment `confirmed`. Leave committing the answers to the run that applies them: a commit whose first line starts with the skill's name would pass for that run ("Re-running a stage").
8. Apply the answers and mark the affected judgments `confirmed`. If an answer overturns a premise, redo the affected part of the draft, then rate the new uncertain points the same way. A redone item keeps its ID while it serves the same purpose, even when its content changes. If an answer drops a drafted item, set its `status: retired`, so that its number is never used again.
   - Answers written under "Unanswered questions" are applied the same way, by the stage's next run or by the agent that wrote the questions when it is continued. Either one reads the answers from the report, and starts from what changed since the commit that left the questions ("Re-running a stage"). Move each answered row to "Decisions" with its number and remove it; the `basis_note` of its items then cites the answer instead of the waiting question. An answer that says how to proceed is applied as it is, even when it leaves a fact open ("keep the draft until the funding review"). Only an answer that cannot be applied, because it is unclear or answers something else, is asked again, as a new question.
   - A question still unanswered, and a new one that the answers raise, is asked during this run when someone can answer it. Otherwise it is written down as in step 7, and the report keeps waiting for answers.
9. When no question waits, check the stage's exit criteria and set the report's status to "answers applied". The items are the source of truth throughout, and the report must match them.
10. Finish the run ("Finishing a run").

## Decisions

The driver ranking, provisional design parameters, decisions that accept a risk, a cost in money or contracts, a weaker driver or a debt, the deferral of a point of the stage's full-depth kinds or of one that rates high, and rejections of findings that leave a risk in place are business decisions as much as technical ones. A design nobody decided on is reopened at the first incident or the first budget review. Rate such a decision like any other point:

- If either rating is high, ask the user to decide. The answer is the decision: mark the judgment `confirmed` and record the question and its answer under "Decisions" in the report.
- Otherwise, adopt the drafted decision provisionally: write a DAS item with `kind: decision`, and mark the judgments that depend on it `assumed`.

Never present a provisional decision as decided. Deferring a point outside the stage's full-depth kinds that does not rate high is not a business decision ("Decision depth").

## Assumptions

An assumption (DAS) records one judgment made without asking: what was drafted, why it was uncertain, and its ratings. Each one is a file in `das/`. The DAS files are shared by the design stages and the review: any of them may record an answer in one.

- Every item that depends on an assumption lists it in `premises`. Find the dependent items by searching `premises`; a DAS does not list them. In a report, "Items that depend on it" means exactly the items whose `premises` name it.
- A DAS is `open` until someone settles it: `confirmed` when the user says it holds, `overturned` when the user says it does not, `retired` when nothing depends on it any more, answered or not (another answer can make it moot). A correction that changes part of an assumption sets `overturned`, records the change in `answer`, and leaves the parts it does not mention as they were drafted, now held.
- On every run, re-rate the open assumptions that this stage's judgments depend on, and update their `breadth`, `severity` and `rating_note` in place, whichever stage wrote them (a QAS is re-rated in this stage's report only: `docs/quality/` is never written). When a judgment you would ask about depends on an open assumption, or items now depend on an assumption so widely that its breadth is high, ask about the assumption in this run, whichever stage wrote it, and record the question and its answer under "Decisions" like any other. Write the answer in the DAS (`answer`, `answered_in`) and set its status. If the answer overturns it, redo this stage's dependent items, and tell the user to re-run the stage that wrote it.
- When the stage that wrote an assumption runs again, it applies the answer recorded in the DAS to its own items: the dependent judgments become `confirmed`, or are redone when the assumption was overturned.
- The quality chain's open assumptions (QAS) follow the same rule, except that the answer cannot be written in `docs/quality/`. When a design judgment you would ask about depends on an open QAS, ask about the QAS, record the question and its answer under "Decisions", and write a request to the quality chain that carries the answer, so that the quality chain applies it on its next run: the QAS in `targets`, the stage that wrote it in `quality_stages`, and status `answered` ("Requests to the quality chain"). The design items that depend on it cite the answer in `basis_note` and are no longer `assumed` on its account; they keep the QAS in `premises` until the quality chain has applied the answer.

## Current state only

Reports and items describe what holds now. They never record how they got there: no sections about earlier runs, no lists of changes, no changelogs, no version numbers, no "what changed" columns, no dates of changes inside items. The history lives in git, and the reasons for each change live in its commit message ("Finishing a run").

- When an answer overturns an earlier decision, replace the earlier row under "Decisions" and keep its number, so that citations of it stay valid; do not keep both.
- The report's header gives the date it was updated and the commit at which its inputs were read (`Inputs as of`): the commit that was current when the run started, or "none" outside git.
- A review report describes the latest review of its stage (for stage 4, of one component). A new review of the same stage replaces it, keeping its decisions in effect and their numbering; findings keep their own status.

## Re-running a stage

- Find what changed since this stage last ran. Its last run is the last commit whose first line starts with this skill's name (`git log -1 --format=%h --grep='^<skill name>' -- <report>`). List the files under `docs/quality/`, `docs/design/` and the code the stage reads that changed after that commit, and read their diffs (`git diff --name-status <commit> -- docs/quality/ docs/design/`, then `git diff <commit> -- <file>`), together with any uncommitted changes. Do not diff from `Inputs as of`: that header records which inputs the report reflects, and a diff from it shows this stage's own last output as changes too. If someone else committed between `Inputs as of` and the skill's commit (`git log --oneline <inputs as of>..<commit>`), read those changes as well. If the project is not under git, or the commits cannot be found, read every input again and compare it with this stage's items.
- A re-run handles what changed: new or changed upstream items (in the quality chain or in an earlier design stage), the open findings addressed to this stage, minor ones included, the open hand-offs addressed to it whose trigger has come, the answers written under its report's "Unanswered questions" ("Draft first, ask afterwards", step 8), the answers recorded in the assumptions this stage wrote, and the requests to the quality chain that were answered or applied ("Requests to the quality chain"). Leave the other items as they are unless a change reaches them. A change that only rewords an upstream item, without changing its meaning, needs nothing here. Keep changes the user made by hand to this stage's items, unless they contradict an input; then ask. To find them, look at the changes to this stage's own files after its last run: one that no skill's commit made, including one not committed yet, is a hand edit; a change made by another skill's commit (its first line starts with the skill's name) is an input. A change inside a generated table is neither: the next run of `scripts/tables.py` rewrites it, except in the cells the report fills in ("Scripts"). An answer given in another stage that changes this stage's items is cited where it is used ("design stage 3, decision 4"); it gets no row under this stage's "Decisions".
- Update in place. Keep existing IDs and never renumber. A new item takes the number after the highest one in use, retired items included.
- When an item is no longer needed, set `status: retired`. Do not delete the file: other items may trace to it. When a retired item is needed again for the same purpose, set it back to `active` instead of writing a new one.
- Artifacts written by an earlier version of these skills may hold content in a form this version no longer uses, and may lack fields that the schemas now have. On the stage's first re-run under this version, move the content of every file the stage wrote into the current form, as `scripts/check.py` lists them (`legacy`, `missing-field`), and drop the old form, keeping no second copy:
  - `changelog`, `version`, `needs_agreement` and `approver_candidates` fields, and sections about earlier runs: drop them. Set the statuses `draft` and `agreed` to `active`; an agreement the file records counts as `confirmed` for what it covered.
  - A report with no `Inputs as of`: read every input again, since there is no commit to diff from.
  - A DEC with `deferred` and `revisit_when`: when `deferred` is true, write a hand-off for what the decision leaves open, with `revisit_when` as its trigger. Then drop both fields.
  - A field that the schema now has and the file lacks: add it, with `null` or `[]` when it has no value.
  - A point under "Open gaps" that is addressed to a later stage, such as a point a quality-chain item leaves for the design to confirm: write a hand-off for it, and remove it from "Open gaps".
  - A MOD with no `depth`: set `depth: full`, and say in `depth_reason` that an earlier version designed every module in full. On the next run of stage 4 for its component, give each such module the depth it gets now, as stage 4 gives a new module one. Cut a module that comes out at bounds depth to what that depth holds: the summary of its contract, `invariants: []`, `behaviour: null`, `parameters: []`, and no section in the component report. Remove from the report's data what keeps no invariant of a module at full depth, except the tables another component reads directly, and retire the assumptions that nothing depends on any more.
  - A report section "Issues for the quality chain", and an issue number in the last column of the SLI bindings table: write a request to the quality chain for each issue that the quality chain has not applied yet, `answered` when the row records the user's answer (such as one about a QAS), and drop the section. In that column, name the request instead of the issue.

  Only the stage that wrote a file moves its content. A later stage that finds such content addressed to it, before that stage has run again, takes it up as it would a hand-off.
- Keep the decisions in effect. Do not ask the same question again unless the inputs it depended on have changed. Number the rows of "Decisions" per stage, and in stage 4 per component report, questions and corrections in one sequence, and continue the numbering on a re-run, so that `basis_note` can cite them ("decision 7", or "question 7" for a question); when citing another stage's, name the stage ("stage 2, decision 4", "stage 4 ELM-02, decision 3"). The rows under "Unanswered questions" share this sequence: a new row in either section takes the number after the highest in both.

### Stale stages

A stage is stale when something it must process has come since its last run (the first point above says how to find that run). The user, and an agent that runs the stages for the user (`design-chain`), decide from this what to run: the stale stages, from the top of the chain down, looking again after each run, since a run can make other stages stale. `scripts/status.py` shows which stages are stale and why, which wait for answers, which reviews are due, and what runs next ("Scripts"). In stage 4, each component counts as a stage of its own: its last run is the last one for the component, and only the inputs, findings and hand-offs that concern the component count. An input concerns a component when it names the component or one of its interfaces, data entities, modules or decisions, when one of these or a driver the component carries names it, or when it binds every component: a technical policy, or a decision that names no element, interface or data entity.

A stage is stale when, since its last run:

- an input it reads was added, changed or retired: an item of the quality chain; an item of an earlier design stage (`design-context.yaml`, DRV, DEC, ELM, POL, IFC, DAT and the specs); or a view, a flow, a budget, a state diagram or a decision table in the report of an earlier stage. For stage 1, an entry that a later stage or a review added to `design-context.yaml` counts too;
- a critical or major finding was addressed to it, and it is still open;
- an open hand-off addressed to it fell due: it was written or passed on to it with this stage's next run as its trigger, or its trigger was an event that has come;
- an assumption that its items list in `premises` was overturned ("Assumptions");
- the quality chain applied a request that its items list in `premises` ("Requests to the quality chain"), or the answer to a QAS that they list there. This shows as a change under `docs/quality/`, which the first point covers.

A stage is also stale whenever a row under its report's "Unanswered questions" has an answer, however it got there: no run has applied it yet ("Draft first, ask afterwards", step 8). A row that asks about a request to the quality chain has its answer also when the request has one, recorded in the request or written under it in the request document. And a stage is stale whenever its report is still a draft: the run that wrote it did not finish, and its next run starts from the files that run left, as the stage's own work.

Nothing else makes a stage stale, though the user may run any stage at any time. Open minor findings wait for the stage's next run ("Findings between design stages"), and so do an answer that confirms one of its assumptions ("Assumptions") and an answer to a request to the quality chain that no row of its report asks about: the change makes the stage stale once the quality chain applies it ("Requests to the quality chain"). A change in the code alone does not make a stage stale: the code holds what implementation decides, and when the code cannot keep a decision of the design, implementation raises a finding, which the second point covers ("Decision depth").

A stage that has never run is not stale; it runs once the stages above it have run. While a stage waits for answers, nothing below it runs, stale or not: no later stage, and no review of it or of a later stage, since the answers may still change what they read. A component of stage 4 that waits holds back only its own review.

Reviews are not stale in this sense. A review runs when "Findings between design stages" calls for one, right after the stage it reviews and before the stages below that stage, as the "Next" of each stage orders them. A review that waits for answers runs again once a row has an answer, and until it has applied its answers, the stages below the stage it reviews wait for it.

## Scripts

Each skill has three scripts in its `scripts/` directory, `tables.py`, `check.py` and `status.py`. They need Python 3.8 or later and no packages. Run them from the project's root, with this skill's directory and name: `python3 <skill directory>/scripts/tables.py --skill <skill name>`. Add `--design <path>` when the design is not in `docs/design/`, and `--quality <path>` when the quality chain is neither where `design-context.yaml` says nor in `docs/quality/`.

- `tables.py` writes the index tables of the reports from the items, so that no table restates an item by hand. A report marks each table it gets from the script with `<!-- generated: <name> -->` and `<!-- /generated -->`, as the report templates show. Do not edit those tables by hand. Some of their cells hold what only the report records, such as how a conflict is resolved or the flow an acceptance criterion passes through; each template names those cells. The script keeps what the report wrote in them, matched by the row's ID, and leaves them empty on new rows for the stage to fill in. It keeps a header row written in the working language, and writes the enum values with the glossary's terms for English and Japanese (for another language, in English). Whatever skill it runs for, it also writes the request document, `quality-chain-requests.md`, from the requests to the quality chain, and stops with a message when the document holds an answer, or other text written by hand, that the requests do not ("Requests to the quality chain").
- `check.py` checks what needs no judgment. Every YAML file parses, and no value is cut off at ` #`. Every item has the fields and values of its schema. Every ID that an item or a report names exists; the IDs in an item's reference fields are of the right kind, and an active item refers to no retired one. The basis matches the premises, and every open DAS has an item that depends on it. Every FR is allocated to a component and carried by an interface, every driver is carried by an element, and every component has a team when the design context names teams. The functions of an interface are among those of its provider, and those of a module among those of its component. Each operation of an interface a component provides is realized by exactly one of its modules. Module dependencies form no cycle. A module at full depth says why in `depth_reason`, and a module at bounds depth has no behaviour section, invariants or parameters. Every HTTP or event interface that a component provides has a spec or a hand-off of its schema to implementation, and each spec matches its IFC in operations, error statuses and error codes. Findings have a valid addressee and resolution, and an accepted finding is cited where it changed items. Hand-offs have a valid sender and addressee, a component when they go to stage 4 or to implementation, a trigger, and a resolution once taken up, and a decided one is cited where it was decided. Conflicts are recorded on both drivers, and every debt has its condition to repay. Every SLI is bound, or names in the report's SLI bindings table an open or answered request to the quality chain that targets it. Once stage 2b has run, every scope of the technical policy has one policy, every component is in one stack and one repository, every dependency rule names its check, and every gate and audit of the quality chain is bound, or named in the report's gate or audit bindings table with an open or answered request that targets it. A request names at least one target and, with a quality chain, the stages that would change it; an answered one records its answer and where it was given; a QAS that an item treats as answered has an answered request that carries the answer. The generated tables are up to date and filled in, and the request document is up to date and holds nothing written by hand that the requests lack.
- `status.py` shows the state of the chain, from the items, the reports and git, and changes nothing: for each stage (each component of stage 4 apart) and each review, its last run, whether it is stale and why ("Stale stages"), whether its report waits for answers, and whether a review is due ("Findings between design stages"); then what runs next. With `--since <commit>` it also counts the runs since that commit and lists the item fields that went back to an earlier value; with `--questions`, the questions that wait; with `--summary`, the open assumptions and what will make a stage stale later. `design-chain` runs the chain by it; anyone can run it to see what to run next.

`check.py` lists each problem under the skill that writes the file it is in: stage 1 writes `design-context.yaml` and `drv/`; stage 2 `elm/` and the decisions of stage `architecture`; stage 2b `pol/` and the decisions of stage `technical-policy`; stage 3 `ifc/`, `dat/` and the decisions of stage `high-level-design`; stage 4 `mod/` and the decisions of stage `detailed-design`; each report and assumption belongs to the stage that writes it; a request to the quality chain belongs to the stage or review that raised it (its `stage`), except its `status` and `answer`, which any run records: with `--skill`, their problems go to that skill; a finding belongs to the skill that raised it, or to implementation when implementation raised it, except its `status` and `resolution`, and a hand-off to the stage that wrote it, except its `status`, `to`, `component`, `trigger` and `resolution`: those belong to the stage it is addressed to. The request document belongs to the run that checks it, since every run rewrites it. With `--skill`, it exits with 1 when that skill's files have problems, and it checks the generated tables of that skill's reports only, since the other reports show the items as of their own stage's last run; it always checks the request document. The review runs it before its activities; a review raises no finding about what it checks.

## Finishing a run

1. List the open assumptions that this run wrote or depends on (DAS and QAS), one line each with their ratings, highest first. Say that no answer is needed, and that any correction the user gives is applied like an answer. Record a correction under "Decisions" with the next number, and set a DAS to `overturned` or `confirmed` as the user says. Silence, or "no corrections", leaves an assumption `open`. When applying the corrections creates new assumptions, list them in the closing message as well. When nobody can answer during the run, the list goes to whoever started it, and a correction that the user gives afterwards is written as a row under "Unanswered questions" with its answer filled in: the question asks whether the assumption holds, and the answer is the correction. The stage's next run applies it like any answer.
2. Tell the user what to run next, following "Findings between design stages": the later stages whose inputs this run changed, and for which items; the stages this run addressed a critical or major finding to, but not a stage it addressed only minor findings to; and, after a run of stage 2, 2b, 3 or 4, the review of this stage (in stage 4, of this component) when there is none yet, or when a critical or major finding changed its items since its last review, whether this stage accepted it or followed an earlier stage that accepted one its review raised. Say also which hand-offs this run wrote, decided or passed on, and which requests to the quality chain it raised, answered, withdrew or found applied. When any request is open or answered, say that `docs/design/quality-chain-requests.md` lists them, for the user to answer and to hand to the quality chain, and name the stages whose items depend on a request this run answered: each follows the answer when it runs. When questions wait for answers, list them by number first, say that this run is resumed once they are answered, and name none of the runs that wait for it ("Stale stages").
3. Run `scripts/tables.py --skill <skill name>`, fill in the cells it leaves empty, then run `scripts/check.py --skill <skill name>`. Fix every problem listed under this skill, and run both again until the check passes. A problem in this stage's items that only an earlier stage can fix is either fixed here or becomes a finding addressed to that stage ("Findings between design stages"); the check then shows it as waiting for that finding. Leave the problems listed under other skills to them, and name them in the closing message with the stage that owns each. When Python 3 is not available, say so in the closing message, check by hand, in the files this run wrote, what `check.py` checks, and write the request document by hand in the form that `artifacts.md` shows.
4. If the project is under git, commit the files this run wrote, and only those, to the current branch. Add the new files, then commit with the paths named, so that nothing else the user has staged is included (`git add -- <paths>`, then `git commit -m "<message>" -- <paths>`). Write the message in the language of the project's recent commit messages, or in the working language when there are none. The first line starts with the skill's name, then says what the run did, so that the next run can find it; the body says what triggered the run, which items were added, changed or retired and why, and what to run next (step 2). When questions wait for answers, the first line says so. Never push. If the commit fails, say so and leave the files as they are.
