## 要約

指摘は 9 件（重大 0、中 4、軽微 5）。宛先は `architecture-to-high-level-design` が 8 件、`architecture-drivers-to-architecture` が 1 件（FND-72）。品質チェーンへの課題は 1 件（FR-12 AC4 の文と、料金が下がる変更）。

前回の指摘 18 件の直しは、数の上ではよく効いている。受け入れ基準 214 件はトレースの表に一行ずつあり、文も IFC の functions とも一致し、前回一部だけだった 23 件はすべて閉じた。HTTP の操作 73 件と、操作ごとのエラーの組 101 件は、仕様書と IFC で欠けも余りもない。PaymentState の 13 値と依頼の state の 10 値は、仕様書と図で一致する。遅延の予算はスクリプトで計算し直してすべて合う。前回の中心だった押さえの結果が分からないときの扱い（FND-30・31・33）は、流れ、エラーの決まり、二つの状態遷移図、DEC-52 で一つにそろった。

崩れているのは、押さえ以外のお金の操作と、押さえの直しの縁:

- FND-70: 手配のトランザクション 1 が見積もりを used にするので、503 PAYMENTS_UNAVAILABLE の後の「同じキーで初めからやり直す」と、402 の後の「別の支払い手段で新しいキー」は、どちらも 409 ESTIMATE_EXPIRED になる。DEC-48 の「何も残さず」も成り立たない。
- FND-71・72: 5xx の後に新しいキーで試す道は、押さえにだけ作られた。確定と取り消しのキーは押さえごとに一つ（DEC-12）で、図は checking → unpaid を「確定していないと確かめた」とする。そのため、確定に 5xx が一度返ると、有効な押さえを残したまま未払いにでき、取り消しの確かめは押さえの期限（7 日）まで続く。
- FND-73: 配信は状態の履歴から作るのに、「押さえがないと確かめた」と「降車場所の変更の取り消し」を履歴に書く種類がない。そのため、FR-05 AC4 と FR-12 AC5 の最後の表示が配信に乗らない。

軽微の 5 件: トレースの書き手の欠け（FND-74）、仕様書の基準の番号が古い（FND-75）、共通の約束事からのずれの残り（FND-76）、not_booked の理由がなく SLI-05 を数え分けられない（FND-77）、報告書と図に残る古い文（FND-78）。

おもなリスクは、Stripe の 5xx（まれだが起きる）で、乗客を、有効な押さえを持ったまま未払いにし、二度目の支払いをさせうること（DRV-04）。項目に書かれた引き換えは、DEC-52 の T_hold_wait 60 秒（押さえられていた手配もやめうる。乗客を最長 60 秒待たせる。DRV-11）、手配をやめた後の新しい手配で押さえが一時に二つになりうること、DEC-51 の Turso の読み出しが 3 倍、DEC-54 の 429 の知らせが入口の枠の尽きと業務の制限を分けないこと。どれも項目と要合意の表にある。
