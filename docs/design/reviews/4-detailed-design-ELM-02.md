## 概要
第 4 段階の ELM-02（担当者とエンジニアの Web アプリ）の最初のレビューで、全体のレビュー。設計を書いた会話とは別の文脈で、成果物だけを読んだ。指摘は 6 件で、中 3 件（`high-level-design-to-detailed-design` 宛て 2、`architecture-to-high-level-design` 宛て 1）、軽微 3 件（どれも `high-level-design-to-detailed-design` 宛て）。質問はなく、品質チェーンへの要求は出しても答えても反映を見つけてもいない。

- FND-43（中）: MOD-01 の begin はアカウントがないと NotSignedIn を返すため、MOD-09 がサインインの前に送る POST /v1/sessions と POST /v1/account-setups を始められず、書かれたとおりでは担当者もエンジニアも使い始められない。合わないパスワードの 401 AUTH_FAILED の扱いも、send の post、状態遷移図、答えの判断表で三通りに食い違う。
- FND-44（中）: MOD-01 はアカウントの変化を同じタブの MOD-09 からしか知らない。セッションのクッキーはタブが共有するので、ほかのタブでほかの担当者がサインインすると、このタブに残った答えのない返金の「もう一度送る」がそのアカウントで送られ、DEC-42 のキーの範囲（アカウントを含む）の外として二度目の返金になりうる（QR-45、DRV-32）。
- FND-45（中、第 3 段階宛て）: EXT-01 が実行の前に退けた返金（処理されなかった、DEC-45）は、返金（DAT-12）の状態遷移図に移り先がなく refunding のまま残る。DEC-45 は新しい試みをはっきりした拒否の後にしか作らず、IFC-13 の retry も答えを決めていないので、担当者がやり直せない（FR-39 の 2）。MOD-02 が受け付ける同じキーの送り直しも、DEC-42 で同じ 503 を受けるだけ。
- 軽微: MOD-01 のタブの保存の項目の決め方（FND-46）、MOD-02 の読み込み中の 429 と知らない符号の 4xx（FND-47）、割り当てと functions の FR-49 の食い違い（FND-48）。

主なリスクは、答えを失った返金を同じキーで一度だけ行うという MOD-01 と MOD-02 の中心の約束が、同じタブの中では成り立つのに、タブをまたいだアカウントの変化（FND-44）と、EXT-01 が処理しなかった返金（FND-45）で破れること。それ以外の確定の深さの設計（MOD-01 の送り直しと答えの分け方、MOD-02 の判断表 B と新しい返金を受け付ける表、二度押し、タブの読み直し、値の計算）は、確かめたかぎり成り立つ。
