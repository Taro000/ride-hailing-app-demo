## 要約

主な設計を動かす要求は 16 件。構造を左右するのは次の 5 件。サーバーはデモの回だけ Cloud Run に出し、毎日の処理はデモの期間だけ Cloud Run のジョブで動かし、ふだんは手元で同じ形で開発する制約（DRV-18）。一人・個人の予算（無料の枠を優先）で作って動かす制約（DRV-26）。お金を確定した額で一度だけ動かし、Stripe の記録と合わせること（DRV-04）。現在地の最新性（DRV-03）。状態の変化をすぐ相手の画面に届けること（DRV-02）。いちばん重い競合は、Cloud Run の動き方（インスタンスの増減、要求の外では CPU が割り当てられない、デモの回にしか動かない）と、送り続ける接続や時刻で動く処理とのぶつかり。期限がないので、主な要求にはどれも実現の道がある。ドライバーを装う人には確認コードで備え（FR-26）、乗客が画面を確かめずに乗る危険と、位置を偽った到着を担当が見落とす危険は、利用者が受け入れた。デモの URL は公開するが、アカウントは参加者にだけ作る（招待制。PC-06）ので、使う人の数は参加者 2 人のまま（PC-05）。最大の危険は一人で抱える量（FR 54 件、NFR 45 件のうちゲート 21 件・人が行う監査 8 件）で、規模（参加者 2 人、全体で乗車 2〜6 回）ではその多くが何も見分けない。それでも量は受け入れて進むと決まった（課題 2、質問 13）。品質チェーンへの課題は 5 件で、すべて決着した。

## 境界と外部

- システム: 乗客の Web アプリとドライバーの Web アプリ（iPhone の Safari）、運営・サポート担当の管理の画面、エンジニアがログと状態の履歴を探す画面、サーバー、時刻で動く処理（突き合わせ、履歴の確かめ、保存期間の処理）、ログとデータ。
- 利用者: USR-01 乗客、USR-02 ドライバー（どちらも iPhone の Safari。ドライバーは受付中に前面に開いておく。デモの参加者は乗客 1 人とドライバー 1 人の 2 人。PC-05。どちらも運営・サポート担当が作ったアカウントに、設定の符号でパスワードを決めてログインする）、USR-03 エンジニア（通知、ログの検索、配備と戻し）、USR-04 運営・サポート担当（参加者のアカウントの作成と設定の符号の出し直し、ドライバーと車両の登録、停止、苦情、返金）。考慮しない利用者: USR-05 経理、USR-06 審査担当（審査の結果はシステムの外で USR-04 に渡す）、USR-07 事業者、USR-08 参加者でない人（デモの URL を見た人。アカウントを持てず、ログインより先に進めない。PC-06。脅威の出どころとしては DRV-29 で扱う）。
- 外部システム: Google Maps Platform（場所の検索、経路と所要時間、地図の表示）、Stripe のテスト環境（押さえ、請求、返金、カードの入力部品）、エンジニアへの通知先（チャットなど。種類だけ決まっている）、ブラウザの機能（位置情報、画面の点灯、音）。
- 実行の場所: デモの回はサーバーを Cloud Run に出し、データは Turso に置く。毎日の処理はデモの期間だけ Cloud Run のジョブで動く（TC-07）。ふだんの開発は手元の機械。CI は GitHub のホストされた CI。
- データを作るもの: 乗客とドライバーの端末（本物の現在地）、Google Maps Platform（経路、所要時間）、Stripe（押さえ、請求、返金の記録）、USR-04（参加者のアカウント、ドライバーと車両の登録、停止、対処、返金）。
- 公開: デモの URL は発表、ブログ、動画で、デモの回の最中や前にも示す（PC-06）。入口を知る人は参加者に限られない。

## 実現できるか

期限がない（PC-02）ので、時間をかければ作れないものはほとんどない。縛りは費用と一人の手間。

## 未解決の点

- Google Maps Platform と Stripe の約束（SLA、上限）は入力にない。Google Maps Platform の無料の枠の大きさに合わせた呼び出しの量は第 2 段階で見積もる。
- R_fare の km と分の刻み、1 円未満の端数、消費税が未定（品質チェーンから）。
- 機能のしきい値（D_pickup_accuracy、T_match_wait、N_rating_levels、D_nearby_drivers、T_noshow_wait、N_min_ratings、T_cancel_grace）は値がない。振る舞いを決める値として、後の段階で提案する。
- エンジニアへの通知先（チャットなど）が決まっていない。
- SLI の操作の名前と経路の対応表は、インタフェースを決める第 3 段階で埋める。
- 迎車（許諾から乗車場所への到着まで）の手順がどの CUJ にもない（品質チェーンから持ち越し）。第 2 段階の通し確認では、CUJ-02 と CUJ-07 の間の流れとして扱う。
- T_request_max（仮に 30 分）は品質チェーンの要合意のまま（FR-08）。T_hold_wait の値は設計が決める（今は第 3 段階の DEC-52 の 60 秒。FR-05・12）。
- 法令、方針、リスク分析の中身を誰も確かめていない（品質チェーンから持ち越し）。DRV-21〜25 は名前と分類だけに基づく。運賃の定めを確かめる人も決まっていない（NFR-43）。
- 参加者の動き方（車か徒歩か）が未定（品質チェーン第 1 段階の質問 19）。DRV-03・12 の環境が変わりうる。
- 質問 15 の前提 3 件（乗車の 2〜3 回はデモ 1 回あたり、状態の履歴の記録に座標を書かない、TC-07 に足した部分も交渉できない）は回答がなく、推定のまま。違っていれば PC-05、DRV-32、DRV-18 を直す。
- デモの期間の延長（TC-07）に上限はない。お金の操作が片付かずに延長が長引いたときに強いて終えることは、第 2 段階の DEC-37 が受け持つ。

## 範囲外

- 参加者から位置情報と個人情報の扱いの同意を得ること: デモの運営の手続き。同意の画面が要るなら、品質チェーン第 2 段階の機能になる。
- デモの回の運営（参加者の集め方、iPhone を持つ人への絞り込み、役割の割り振り）: 業務の手続き。
- 設定の符号を参加者本人に渡す手段（手渡しなど）: 運営・サポート担当の手続き。システムは符号を示すところまで（FR-48）。
