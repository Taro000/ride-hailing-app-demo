# 設計を動かす要求: 配車サービス

状態: 回答反映済み · 更新: 2026-11-13 · 入力の基準: 9ace3f3 · 第 1 段階（全 4 段階）

## 概要
主な設計を動かす要求は 12 で（質問 6 で決めた順）、iOS の Safari の Web アプリという制約（DRV-14）、流れの可用性（DRV-01）、現在地の新しさ（DRV-04）、お金の正しさ（DRV-07）、相手への速い表示（DRV-03）、Cloud Run と Turso を想定してローカルだけで動かすこと（DRV-15）、開発者 1 人と個人の費用（DRV-16）、本人の確かめ（DRV-28）、個人の情報の保護（DRV-29）、依頼の状態を一つに保つこと（DRV-02）、一件の依頼のたどり（DRV-24）、変更のとどめ方（DRV-12）。もっとも難しい競合は DRV-14 と DRV-04、DRV-03 の間で、Web アプリはアプリが前に出ていない間に位置も変化も扱えないため、事業は、乗客とドライバーが迎車を待つ間から乗車中まで、ドライバーは受付をしている間もアプリを画面に出したままにすると決めた（決めたこと 2 と設計の第 2 段階の質問 2、TC-18。QCR-02 と QCR-03 で品質チェーンに記録を求めた）。どの主な要求にもこの費用と体制で知られたやり方があるが、DRV-04 と DRV-03 はその使い方を条件にし、本番は Cloud Run と Turso を想定して設計するだけで配備しないため、SLO、監視、監査は実際には行われない（決めたこと 1）。設計の与件で欠けているのは開発者が使いこなす技術だけで、DAS-01 で仮定した。

将来の変更は、利用者が「特になし」とした。変更のシナリオは保守性と移植性の品質要求から書いた（DRV-12、DRV-13）。費用は額が決まっておらず、個人が払える程度（PC-01）なので、実現できるかはこの見方で確かめた。
