# CUJ-01 の縦の一本: 設計の細部の使われ方

更新: 2026-11-10。[Taro000/req-to-design#4](https://github.com/Taro000/req-to-design/issues/4)（0.3.0 の 0）の作業。入力は `docs/design/` の今の成果物（0.1.0 の連鎖の出力。PR #2 のマージの時点）。

## 要約

CUJ-01（配車手配）の主な流れと、失敗の流れを一つ（押さえの結果が分からないとき）を、ELM-01（乗客の Web アプリ）と ELM-04（サーバー）で実装した。Stripe と地図は偽物（DEC-25 の差し替え口）。テストは単体と結合が 68 件、画面の自動テストが 5 件で、どれも通る。

触れた設計の細部を 147 行に分けて記録した。そのまま使ったのは 92 行、変えたのは 13 行、使わなかったのは 42 行（範囲外 31 行、範囲の中なのに要らなかった 10 行、要るが作らなかった 1 行）。ほかに、設計が決めておらず実装で決めたことが 24 件あった。

言えることは三つある。

1. インタフェースの約束（API の形、エラーの決まり、冪等キーの意味、利用側に見える状態の値、配信の出来事）と、第 2 段階の仕組みの原則は、ほとんどそのまま使えた。ELM-01 と ELM-04 を別々に書いても、この約束だけでつながった。変えた 13 行のうち利用側に見える約束に触れたのは 4 行で、3 行は写しや別々の細部の食い違い、1 行は文の書き方だった。早く決めてよかった種類。
2. 変えた 13 行のうち 8 行は、ほかの要素から見えない中の作り（配信の追いかけ方、確かめの時刻、属性の一覧など）、3 行は別々の所に書いた細部どうしの食い違いだった。早い段で細部まで決めるより、守る枠だけを決めて実装に送るべきだった種類。
3. 物理データは設計がまったく決めておらず（ELM-04 の第 4 段階はない）、実装で決めて困らなかった。困りそうだったのは、お金と並行性の不変条件を一意の索引で守る所だけで、それは論理データ（DAT-06、DAT-13）の整合の取り方に書いてあった。

## 作ったもの

### 範囲

| 流れ | 中身 | 機能 |
|---|---|---|
| 主な流れ | ログイン → 乗る場所と降りる場所を探して選ぶ → 見積もり（到着予定時刻、所要時間、料金の内訳）→ 手配の確定（押さえ）→「ドライバーを探しています」→ 許諾の前の取り消し（無料、押さえを解放） | FR-01 AC3・5、FR-02 AC2・5・6、FR-03 AC1〜6、FR-05 AC2・3・5・6、FR-06 AC3、FR-07 AC1 |
| 失敗の流れ | 押さえの結果が分からない（タイムアウト、届かなかった、Stripe の 5xx、インスタンスが途中で止まった）→ 202 HOLD_PENDING と「支払いを確かめています」→ 見回りが Stripe の一覧で照らす → 押さえていれば searching、届いていなければ同じキーで、5xx の後は T_op_stale を過ぎてから新しいキーで送る → T_hold_wait を過ぎたら手配をやめ、押さえは確かめを続け、ないと分かってから「押さえていません」。確かめ中の取り消し（202 HOLD_RELEASE_PENDING）と、後で見つかった押さえの解放 | FR-05 AC4、DEC-52 |

許諾から後（ELM-02 のドライバーの画面がない）、T_match_wait と T_request_max、しきい値、近くの数、現在地とピン、地図の表示、設定の符号と支払い手段の登録、毎日の処理、配備は範囲の外。

### 動かし方

```sh
npm ci
npm run check        # 型、Oxlint、Oxfmt、依存の規則、Vitest
npm run test:e2e     # SPA を組み立て、サーバーが配り、Playwright（Chromium）と axe で通す
npm run dev:server   # :8080。手元の乗客（passenger@example.com / demo-password-123 ほか）を作る
npm run dev:web      # :5173。/api をサーバーへ中継する
```

手元の乗客は、偽物の Stripe の筋書きを支払い手段で選ぶ（`timeout@example.com` はタイムアウトの後に押さえが見つかる、`lost@example.com` は Stripe に届かない、`unresponsive@example.com` は一覧がしばらく答えない、`declined@example.com` は断られる、`nocard@example.com` は支払い手段がない）。

### 確かめたこと

- `npm run check` が通る。単体と結合が 68 件（ドメイン 21、サーバー 28、画面 19）。
- 画面の自動テスト 5 件が通る。主な流れ、失敗の流れの三つ（見回りが見つける、T_hold_wait で手配をやめる、確かめ中に取り消す）、断られたとき。axe の WCAG 2.2 AA の違反は 0。
- 失敗の流れのサーバーの筋書き 7 つ（タイムアウトの後に見つかる、届いていない、5xx の後に新しいキー、Stripe が答えない、確かめ中の取り消し、インスタンスが止まった、一つの確かめが失敗してもほかを続ける）。
- 冪等キー: 同じキーで同じ結果、動いている間は 409、違う中身は 422、503 PAYMENTS_UNAVAILABLE はキーを放して同じキーで初めからやり直せる。
- 経路の上限: T_route で 503 ROUTE_TIMEOUT を返しても中の処理は続き、同じキーの送り直しで最初の結果を受ける。
- ログに座標、検索の語、メールアドレスが出ない。依存の規則の違反が 0。

### 確かめていないこと

- 本物の Stripe と Google Maps（テスト環境にも向けていない）。押さえの応答時間、Stripe の一覧の振る舞い、地図の割り当ては偽物の作りを信じている。
- Turso Cloud（手元の libSQL のファイルだけ）。T_db の fetch の中止は書いたが動かしていない。
- iOS の Safari（TC-09）。画面の自動テストは iPhone の大きさの Chromium。Safari の裏に回ったときの配信も見ていない。
- インスタンスが二つ並んだときのリースと条件付きの書き込み（テストは一つの処理の中で重ねただけ）。
- Cloud Run への配備、CI（`.github/workflows/ci.yml` はこの PR の確かめのための最小のもので、ELM-06 の CI のゲートではない）。

## 記録の決まり

- 区分は Issue の三つ。「使わなかった」は理由を三つに分けた。**範囲外**は縦の一本が触れない流れ（「範囲」の表で外したものを含む）のためで、要らないとは言えない。**範囲内で不要**は、縦の一本の中にあるのに実装が読まずに済んだもの。**範囲内で作らなかった**は、要るが作れなかったもの。
- 設計が決めておらず実装で決めたことは、別の表にした（区分に入れない）。
- 段は、その細部を決めた段。1 は第 1 段階（`design-context.yaml` の制約）、2 は第 2 段階（DEC-01〜37）、3 は第 3 段階（DEC-38〜55、IFC、DAT、仕様書）、4 は ELM-03 の第 4 段階（DEC-56〜66 と、ELM-03 の報告書が web-shared に求めた約束）。
- 一行に細部を一つ書いた。範囲外で使わなかったものは、項目ごとに一行にまとめた。そのため「使わなかった（範囲外）」の数は少なめに出る。

細部の種類:

| 種類 | 中身 |
|---|---|
| 構造 | 要素、コードの分け方、依存の規則、差し替え口 |
| 技術の選定 | ランタイム、フレームワーク、ライブラリ、道具 |
| 外部との統合 | 外部 API の使い方、キー、メタデータ |
| 仕組みの原則 | 冪等、結果不明の扱い、トランザクションの分け方、条件付きの書き込み、見回り |
| 状態遷移 | 状態の値と遷移 |
| 判断表・手順 | 分岐の決まり、手順図の中身 |
| エラーの決まり | エラーの形、符号、状態の符号、呼ぶ側の扱い |
| 冪等キーの細部 | どの要求に付けるか、最初の結果、例外、保つ期間 |
| 値 | タイムアウト、間隔、閾値、長さ |
| API のスキーマ | 操作の一覧、要求と応答の形 |
| 配信の形 | 出来事、カーソル、出どころ、つなぎ直し |
| 論理データ | 実体、属性、持ち主、整合の取り方 |
| 物理データ | 表、列、索引、持つ形 |
| 共通の約束事 | ID、時刻、お金、命名、設定 |
| 画面 | 画面の流れ、文言、部品 |
| 観測 | ログ、トレース、測定点、遅延の予算 |
| 認証・守り | ログイン、セッション、送り元、回数の制限 |
| 根拠 | 案の比べ、退けた案、計算 |

実装して見つかった食い違いは 4 つ。どれも、細部を複数の所に書いたことか、別々の細部の組み合わせを誰も通していないことから来ている。

## そこから言えること（2-1 への入力）

### 早く決めてよかった種類

- **インタフェースの約束**（API のスキーマ、エラーの決まり、冪等キーの意味、利用側に見える状態の値、配信の出来事）。ELM-01 と ELM-04 を別々に書き、MSW の偽のサーバーで画面を、`app.request` でサーバーを確かめ、最後に画面の自動テストでつないだが、つなぐときに直した所はなかった。ここは第 3 段階の「確定」のままでよい。
- **第 2 段階の仕組みの原則**（状態を持たない、トランザクションは外部の呼び出しをまたがない、冪等の三重、結果不明は確かめ中、配信の出どころは履歴、差し替え口）。コードの形をいちばん強く決めた。第 2 段階で変えたのは 2 行だけで、仕組みの原則では DEC-12 (d) の時刻の扱い一つ。#7 のたたき台の「仕組みの原則」は確定でよい。
- **結果不明の呼び出しの分け方**（DEC-52 の三つの分け方と「押さえていないと言うのは Stripe が答えたときだけ」）。お金の結果不明の扱いは、偽物とテストの筋書きを決める入力そのものだった。結果の分け方と利用者への見せ方（インタフェースに出る所）は第 3 段階で確定、確かめの手順の判断表は第 4 段階、の分け方が合う。

### 早く決めたが変えた種類（枠にとどめるべきだった）

変えた 13 行は、第 3 段階が 11 行、第 2 段階が 2 行。第 4 段階（ELM-03）の決定で変えたものはない。

- 8 行は、ほかの要素から見えない中の作りだった（配信の追いかけ方、確かめの時刻、属性の一覧など）。段が決めるべきだったのは枠（「配信は履歴の通し番号から、取りこぼさない」「確かめ中を片付けるのは、最後に送った要求が終わったと言えてから」「起きていないと扱う結果では、一つ目のトランザクションで書いたものをすべて戻す」）で、属性と一覧は実装に送ってよかった。属性の一覧（DAT の key_attributes）は、使った属性はそのまま使えたが、足りない属性が 4 つ出た（last_sent_at、estimate_id、依頼の cancelled_by と cancel_reason）。

### 先送りしてよかった種類

- **物理データ**。設計がなく、実装で表 9 つを決めて困らなかった。不変条件（進行中の依頼は一つ、同時に動くお金の操作は種類ごとに一つ）は論理データの整合の取り方に書いてあり、それを部分の一意の索引にしただけ。#7 のたたき台の「第 4 段階はお金、結果不明、並行性を含むモジュールの物理データ」は、不変条件を守る所に絞ってよい。
- **タイムアウトと間隔の値**。使った値（T_route、T_op_stale、T_hold_wait、P_tail、生存確認、ブラウザ 15 秒）は結果の数だけで足り、それを出した計算（遅延の予算、最悪の 13.0 秒）は読まなかった。外部の呼び出しの値（Stripe 2.5 秒、地図 2 秒）は、設計自身が「測ってから見直す」としている。値は申し送りでよく、段が決めるのは順の約束（ブラウザ > サーバー > 中の呼び出し、T_op_stale > 処理が続きうる最長）だけでよい。
- **ライブラリの細部**。Better Auth（DEC-20 の候補）は要らず、ELM-03 の第 4 段階が選んだ TanStack Query（DEC-57）も ELM-01 には要らなかった。ほかの部品の第 4 段階が web-shared を通じて別の部品のライブラリを縛る形は、合わないことがある。選定は 2b に集め、使うかは実装に任せる。
