## 未解決の点
- FR-19、FR-20、FR-32 の「現在地から乗車場所までの距離」が、道のりか直線かは決まっていない。第 3 段階の QR-32 の失敗のシナリオに関わる。
- セキュリティのリスク分析の中身は確かめていない（第 3 段階の質問 1）。分かると、第 3 段階がその入口の品質要求を加え、機能の提案が来うる。
- CUJ-14〜CUJ-18 に手順がないため、その FR は cuj_step を空にした。手順が決まったら第 1 段階で CUJ に手順を加え、この段階で FR を手順に結び付け直す。
- 第 1 段階へ: 共有する事実に CON-08（キャンセル料と不在の料金）が加わった。QIU-04 の「確認した料金を超えて請求されない」が、乗車に至らなかった依頼の料金をどう扱うかは決まっていない。評価は 1〜5 の 5 段階（質問 9）なので、QIU-06 の N_ride_rating_ok「評価の上位 2 段階」は 4 と 5 にあたる。
- 第 1 段階へ: QIU-05 の測定量のデータは FR-45（手配時に示した到着予定時刻と到着を確認した時刻）が作る。QIU-05 の basis_note はまだその FR を名指ししていない。
- 第 3 段階へ: QR-41 は、乗客とドライバーが苦情、返金の求め、報告を寄せるとしているが、寄せるのは自分の乗車についての乗客だけ（第 1 段階の質問 7）で、FR-37 はそれに合わせた。

## 範囲外
- ドライバーと車両の審査そのものと、その結果の記録: システムの外の運営の手続きで行い、結果はシステムに記録しない（CON-07）。システムは登録したドライバーにだけ依頼を届け（FR-43）、誰が登録したかを記録する（FR-50）。
- 苦情の中身の判断と、返金を認めるかどうかの判断: 担当者が行う判断で、ソフトウェアでは満たせない。システムは受け付け、記録し、返金を行う（FR-37〜FR-40）。
- 障害の原因の特定、機能の追加と修正、利用技術のバージョンアップへの対応そのもの: エンジニアの作業で、ソフトウェアの機能ではない。システムは知らせる、たどる、止める機能で支える（FR-33〜FR-36、FR-52）。
