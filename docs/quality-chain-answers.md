## 答え

### 設計 1-1 常時稼働の前提

答え: 課題の案どおり。

- context.yaml の運用の事実に「サーバーはデモの回と確かめの短い間だけ動き、毎日の処理はデモの期間だけ動く（設計の TC-07）」を足す。
- NFR-01〜45 の conditions.workload の「常時稼働し、使うのはデモの回だけ」を「サーバーはデモの回だけ、毎日の処理はデモの期間だけ動く」に直す。
- NFR-01〜03 のアラートの condition から「デモの回の外では呼び出しをチケットに変える」を外す。回の外にはサーバーがなく、出来事も起きない。
- QIU-28〜30 の「本番に出す」を「main に入って CI が通り、次のデモの回に配備できる状態になる」として測る。次の回を待つ時間は含めない。T_lead_feature、T_lead_fix、T_lead_upgrade の値は変えない。

### 設計 1-3 Android

答え: 課題の案どおり（対象を iOS の Safari だけにしたのは、設計の第 1 段階の質問 10）。

- QR-42: 対象を iOS の Safari だけにする。Android の Chrome を外す。
- NFR-20: リリース前の確かめは、参加者が使う iPhone の iOS の版で行う。一つ前の主要な版は確かめない。
- NFR-21: Android の Chrome を対象外のブラウザとして扱う（使われたら知らせる側に入る）。
- NFR-26: 電池の確かめは、ドライバーが使う iPhone で行う。

### 設計 1-4 古い記述（仮のスタブ）

答え: 課題の案どおり。課題が挙げた項目のほかにも同じ記述があるので、まとめて直す。

- context.yaml の制約: 決済は Stripe のテスト環境（サンドボックス）と書き、「選ぶまでは自作の仮のスタブで代わりにし、最初のデモの前にテスト環境へ差し替える」を外す。
- context.yaml のデータを作るシステム: 地図・経路・渋滞の情報は Google Maps Platform、決済は Stripe のテスト環境と書き、「選ぶまでは自作の仮のスタブ」を外す。
- NFR-44: 「仮のスタブではなく」を外す。最初のデモの前に、Stripe のテスト環境につながっていることと、FR-55 が記録を取り出して突き合わせられることを確かめる形にする。
- SLI-04: lifecycle の「差し替えた日の翌日から数える」を「最初のデモの回の日から数える」にし、blind_spots の「差し替えまでは値がない」を外す。
- NFR-04・07、FR-55、QR-32: basis_note の差し替えとスタブの記述を直す。

### 設計 1-5 乗客がドライバーを確かめる

答え: 新しい機能は足さない。今の確認コードを、両方向の確かめに使う。

- FR-26 に受け入れ基準を足す。「迎車中の乗客の画面に、乗る前に確認コードをドライバーに伝え、画面が乗車中に変わってから乗るよう示す。変わらなければ手配した車ではないと案内する」。コードは手配したドライバーのアプリでしか通らないので、画面が乗車中に変わることが、乗客にとってドライバーの確かめになる。
- QIU-05 を支える手立てを、FR-09（顔写真、車種、色、ナンバー）と FR-26 とする。
- 残る危険（乗客が画面を確かめずに乗ると防げない）は受け入れる。

理由: 本物の配車サービスと同じ形で、作るものが増えない。参加者が顔の分かる 2 人のデモでは、装う人はいない。

### 設計 2-1（設計 3-3 を含む）押さえの結果が分からないとき

答え: FR-05 と FR-12 に扱いを足す。設計 3-3 の具体の形（DEC-52）に、設計の指摘 FND-31 の勧めを合わせる。

- FR-05 に受け入れ基準を足す。「押さえの結果が分からない（決済のサービスが答えない）ときは、依頼をドライバーに示さず『確かめています』と示し、乗客が取り消せるようにする。T_hold_wait までに押さえたと分かれば、依頼をドライバーに示す。分からないまま T_hold_wait を過ぎるか乗客が取り消したら、手配をやめたと示し、押さえが残っていれば解放する。解放したか押さえがないと分かるまでは『押さえが残っていれば解放します』と示す。『押さえていない』と示すのは、決済のサービスが答えたときだけ」。
- FR-12 にも同じ扱いを足す。間に合わなければ降車場所を変えず、新しい押さえが残っていれば解放する。
- T_hold_wait の値は設計が決める（今は DEC-52 の 60 秒）。

### 設計 2-2 疑わしい到着の料金

答え: 料金の規則は変えない。位置の列から偽りが疑われる到着（設計の DEC-29 が印を付ける）にも、今の規則どおりに不在の料金とキャンセル料をかける。運営・サポート担当が毎日の一覧で見て、偽りと判断したら返金する（FR-50）。

- QR-49 に「疑わしい印の付いた到着の料金は、運営・サポート担当が一覧で見て、偽りなら返金する」を足す。
- NFR-45 の一覧に疑わしい印を足し、疑わしい到着の件数もドライバーごとに数える。
- FR-07・27 と NFR-07 は変えない。

理由: 新しい処理が要らず、設計（DEC-29）もこの形になっている。自動で無料にすると、位置の誤差で誤って印が付いたとき、ドライバーが正しい料金を失い、取り戻す手段がない。

### 設計 2-3 FR-45 の「経路」

答え: 課題の案どおり。

- FR-45 の「経路」を「記録した位置で示す」と書く。示すのは、状態の履歴に残る位置（迎車の到着、乗車の開始、不在、乗車の終了）と、T_log_retention（28 日）の間は位置の受信の記録。Google の経路は持たない。
- 保存期間は変えない。デモは 1 回が 1〜2 日で、苦情はデモの期間の中で扱うので、28 日で足りる。

### 設計 2-5 位置のない変化

答え: 課題の二つの案を合わせる。

- FR-39 AC1: 位置を記録するのは、ドライバーが場所で行う四つの操作（迎車の到着、乗車の開始、不在、乗車の終了）だけにする。四つで現在地を得られなかったときは、得られなかった印を記録する（迎車の到着では、FR-25 AC3 の「位置を確かめられなかった」）。
- ほかの変化（手配、許諾、取り消し、降車場所の変更、請求、返金、システムが起こす変化）には位置を求めない。
- SLI-05 の COMPLETE と NFR-05: 四つの操作は、位置か得られなかった印があればそろったと数える。ほかの変化は、時刻と操作した人があればそろったと数える。

理由: 全体で乗車 2〜6 回の規模では、正しく起きた変化を 1 件「欠け」と数えるだけで 99% を割る。

### 設計 2-6 押さえ直しと二重の押さえ

答え: 課題の案どおり（押さえ直しは、設計の第 2 段階の質問 3 で決めた DEC-11）。

- QR-09 の「二重の押さえ」から、料金が上がる降車場所の変更での押さえ直しを除く。
- NFR-07 の誤りの「同じ乗車への二度目の押さえ」を、「押さえ直しの後も古い押さえが取り消されずに残るもの」と「同じ押さえ直しに二つ目の押さえがあるもの」に直す。

### 設計 2-7 誰も終えない依頼

答え: 上限を過ぎたら、システムが自動で終える機能を足す。

- FR-08 に受け入れ基準を足す。「手配から T_request_max を過ぎても許諾がない依頼は、乗客が待ち続けることを選んでいても、システムが取り消す。押さえた額をすべて解放し、キャンセル料はかけず、乗客に知らせる。取り消したのはシステムと記録する（FR-39）」。
- T_request_max は新しい未定の値。仮に 30 分とし、T_match_wait より長くする。
- 許諾の後に誰も終えない依頼は、この機能では扱わない（設計の DEC-37 の、閉じる前の確かめのまま）。

理由: 今の FR-08 では、依頼の状態に出口がない。デモの規模に関係なく欠陥で、時刻で決まる規則（設計の DEC-04）に一つ足せば済む。

### 設計 2-8 SLI-03 の確かめられなかった分

答え: SLI-03 を、設計（DEC-16 の版 4、設計の第 2 段階の質問 24）に合わせて書き直す。課題の案のように counting_rule に一文足すだけでは、「サーバーが確かめる 1 回」という単位と食い違うので、単位から直す。

- unit_event: 「使用中の参加者 1 人の、毎分 0 秒の時点 1 回。使用中の区間は受付と状態の記録で決め、デモの回が開いていた間に限る」。
- method: 受信の時刻法（毎分 0 秒の時点と、その時点より前に最後に受けた現在地の時刻の差）。
- CHECKS の counting_rule: 「毎分 0 秒の時点ごとに、使用中の参加者 1 人を 1 件と数える。サーバーが確かめられなかった分（サーバーが止まった間、Turso に届かなかった間）も、位置の受信の記録と受付・状態の記録から同じ規則で確かめ直して数える。受信がなければ新しくないと数える。後から届いた裏の記録も除く」。今の除くもの（裏にあった時間、受付を始めてから最初の 30 秒、テスト用アカウント）は変えない。
- blind_spots に二つ足す。
  - サーバーが止まっていた間は、最後の状態のまま使用中とみなして数えるので、実際より悪く見えうる。
  - アラート（サーバーの毎分の確かめ）と毎日の値はずれうる。ずれるのは、サーバーが確かめられなかった分と、後から届いた裏の記録。
- NFR-03 の文と目標は変えない。

### 設計 2-9 参加者でない人の登録と利用

答え: 乗客のアカウントも、運営・サポート担当が作る（招待制）。ドライバーと同じく、運営・サポート担当がアカウントを作って一度だけ使える設定の符号を渡し、乗客はその符号でパスワードを決めてログインする。乗客が自分でアカウントを作る流れはなくす。参加者でない人の利用は許さない。

- context.yaml の制約に足す。「アカウントは、運営・サポート担当が参加者にだけ作る。デモの URL は発表、ブログ、動画で、デモの回の最中や前にも示すが、参加者でない人はログインより先に進めない」。
- context.yaml の利用者に「参加者でない人（URL を見た人）」を、考慮しない利用者として載せる。理由は「アカウントを持てない」。
- FR-01: statement と AC1・AC2 を直す。乗客は、運営・サポート担当が作ったアカウントでログインする。AC2 の重複の確かめ（同じ連絡先のアカウントがすでにあるとき）は、運営・サポート担当が作るときに移す。テスト用の印（AC5）は変えない。
- FR-48: 乗客のアカウントを作る流れを足す（乗客の名前と連絡先を入れると、一度だけ使える設定の符号を出す）。FR-48 に足すか新しい FR にするかは、第 2 段階が決める。
- SLI-01〜05 と NFR-01〜05 には、参加者の印を足さない。ログインできるのは参加者とテスト用アカウントだけになる（SLI-01 の VALID はもともと「ログインした参加者からのもの」）。
- 第 3 段階は、変わった FR-01・48 に追随する（QR-20 で、設定の符号が本人だけに届くことなど）。

理由: 公開した URL のまま自分で登録できると、知らない人のメールアドレスと乗る場所を、通知も同意もなく持つことになる。ドライバーのための設計済みの仕組み（`POST /api/v1/admin/drivers`、`POST /api/v1/auth/driver-setup`）がそのまま使える。設計 3-1 も消える。

### 設計 3-1 登録の画面でアカウントの有無が分かる

答え: 設計 2-9 の答えで消える。乗客が自分で登録する画面がなくなり、重複の理由は、アカウントを作る運営・サポート担当にだけ示す。QR-20 は、この課題のためには変えない。

### 設計 3-2 失敗した返金をやり直すときのキー

答え: 課題の案どおり。FR-50 AC4 を「決済のサービスが答えず送り直すときは、同じキーを使う。返金に失敗したと分かった後にやり直すときは、新しい返金の要求（新しいキー）にする」に直す。同じキーで送り直しても、Stripe は同じ失敗を返すため。

### 設計 3-3 DEC-52 の扱いを FR の基準に

答え: 設計 2-1 と一つにした（そちらを見る）。

### レビュー 3-1 NFR-25 の数え方

答え: 課題の案どおり。NFR-25 の signal を「乗車の終了と、請求の結果（成功か失敗）の記録の時刻の差。10 秒以内に結果がないもの（確かめ中）も、超えたと数える」に直す。

## 品質チェーンのあとで設計の連鎖が扱うもの

品質チェーンを回し終えたら、設計の連鎖を第 1 段階から追随させる。答えから見込める変更は次のとおり（決めるのは各段階の再実行）。

- 第 1 段階（`requirements-to-architecture-drivers`）: FND-27 を片付ける。URL を公開する事実と示す時期を、設計の前提に書く。招待制なので PC-05 は使う人の数の上限のまま使える。DRV-29 の応答に「参加者でない人はログインより先に進めない」を足し、環境には URL の公開で攻撃が起きやすくなることを書く。
- 第 2 段階（`architecture-drivers-to-architecture`）:
  - DEC-21 の負債を返す。流れの優先と地図の取り置きは外せる見込みで、アカウントの作成の回数の制限は要らなくなる。
  - DEC-30 の先送りを閉じる（設計 1-5）。
  - DEC-04 に T_request_max の規則を足し、DEC-37 の (B)（サービスか参加者でしか片付かない残り）を縮める（設計 2-7）。
- 第 3 段階（`architecture-to-high-level-design`）:
  - IFC-01（`POST /api/v1/auth/signup`）を外す。管理の画面に乗客のアカウントの作成を足し、設定の符号の入口を乗客にも使う。
  - `GET /api/v1/config` がログインなしで地図のブラウザの鍵を返すのを、ログインの後に回すかを決める。
  - FND-31（DEC-52）を、設計 2-1 の答えの形で片付ける。FND-35（NFR-25）と FR-50 のキーも、この答えに合わせる。
